Projects/Quantized LLM Runtime
Inference Runtime · In Progress

高性能 LLM 量化推理 Runtime：把量化格式、Kernel 与模型执行连成一条链。

面向 Llama / Qwen 等 Decoder-only 模型，使用 PyTorch Extension 封装 CUTLASS Kernel，探索 W8A8、FP8 与 AWQ 的权重/激活表示、GEMM、Decode GEMV、内存布局和端到端执行。该项目仍在持续完善，首版不写尚未完成的性能结论。

01 / Goal

目标不是重写一个完整 vLLM，而是理解高性能推理 Runtime 的关键边界。

项目通过一个可控的小型 Runtime，拆解模型加载、量化参数、线性层替换、Kernel dispatch、workspace、KV Cache 与 decode 执行。这样可以更直接地回答：某种量化为什么省显存、计算是否真的更快、数据转换成本在哪里、Kernel 优化能否转化为端到端收益。

当前原则

先保证数值正确和接口清晰，再比较 Kernel；先建立 FP16 baseline，再分别引入 W8A8、FP8 与 weight-only 路径，避免多个变量同时变化。

02 / Architecture

Runtime 模块

Model LoaderHF weights / config
Quant Packscale / zero / layout
PyTorch ExtensionC++ / CUDA binding
Kernel BackendCUTLASS GEMM / GEMV
Runtime Loopprefill / decode / cache

Linear 层是主要切入点：权重预处理后，Runtime 根据 batch、M/N/K、dtype 与量化策略选择 GEMM 或 GEMV 路径。Prefill 与 Decode 的算术强度和形状不同，不能用同一个“最优 Kernel”概括。

03 / Quantization

三条量化路径解决的问题不同

PathRepresentationMain BenefitMain Cost / Risk
W8A8INT8 weight + INT8 activation高吞吐 GEMM、较低带宽激活量化、scale 与精度控制
FP8FP8 weight / activationHopper Tensor Core 友好格式选择、动态范围与缩放
AWQ低比特 weight-only显著降低权重显存与带宽反量化融合、group scale、decode 路径

项目重点关注量化参数的数据结构与布局是否匹配 Kernel 读取模式，以及反量化、cast、transpose 等“非 GEMM”操作是否吞掉理论收益。

04 / Kernel

Prefill GEMM 与 Decode GEMV 需要分开设计。

Prefill

M 较大，适合使用 Tensor Core GEMM；重点是 tile、pipeline、layout、epilogue 与量化 scale 融合。

Decode

M 接近 1 或小 batch，容易变成 memory / launch bound；需要评估 GEMV、persistent kernel、权重读取与 batch 聚合。

Correctness

与 PyTorch FP16/FP32 reference 比较 max error、relative error、token logits 与生成结果。

Performance

分别统计 Kernel latency、E2E latency、tokens/s、显存与转换开销，避免只展示单算子峰值。

05 / Current Status

目前已经完成与正在补齐的部分

  • 建立轻量 Runtime 与 PyTorch Extension 的基本代码结构。
  • 完成 CUTLASS W8A8 / INT8 GEMM 的封装方向与 Linear 层替换设计。
  • 设计量化权重、scale 与内存布局的基本数据结构。
  • 补齐 FP16、W8A8、FP8、AWQ 的统一 correctness suite。
  • 完成 Prefill / Decode 分开的 E2E latency、throughput 与 memory 对照。
  • 增加不同模型、batch、sequence length 与 GPU 架构的自动化 benchmark。
为什么不在首版写“提升 X%”

目前缺少在统一环境、统一 baseline 和完整 E2E 口径下整理好的最终数据。单个 CUTLASS Kernel 的速度不能直接代表 Runtime 或模型生成性能，因此暂不写结论性数字。

07 / Learning

这个项目要证明的能力

  • 理解模型量化不是“把 FP16 转成 INT4”，而是一整套 calibration、scale、layout、Kernel 与精度权衡。
  • 能够使用 PyTorch C++/CUDA Extension 把自定义 Kernel 接入模型执行。
  • 能够区分 Prefill 与 Decode 的性能特征，不用单一 GEMM benchmark 代替推理系统分析。
  • 能够建立从单算子到端到端的性能账本，判断优化收益被哪些转换和调度成本抵消。
